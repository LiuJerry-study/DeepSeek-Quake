## ✅ 根因已找到并修复（2026-10-07 第二轮审计）

### 用户报告的现象

> 在窗口里**右键点击「非直接复制的区域」**（空白处、非输入框、非可选文本）之后，
> **双击 Ctrl 收不回去**，而且**除了这个窗口，别的页面也点不动**。
> 「一下就卡住」。

### 根因一（主因）：右键吞掉抬起 → 鼠标状态永久中毒 → 双击被无声否决

用户说的「一下就卡住」正是这个：**一次右键就够**，此后双击 Ctrl 完全无效，只能重启进程。

链路（每一环都有实测）：

```
用户在窗口里右键
  └─ 右键粘贴的钩子吞掉 WM_RBUTTONUP（return 1，为的是不让 Chrome 弹原生菜单）
       └─ 系统侧 GetAsyncKeyState(VK_RBUTTON) 的 0x8000 位**永远挂着**（没人清）
            └─ HotkeyManager 的旧判据 Native.IsAnyMouseButtonDown() 从此**恒为真**
                 └─ HandleKey 的 up 分支走「这一轮是鼠标手势」→ `_tapPending=false`
                      └─ 第一敲永不武装 → 此后**每一次双击都被静默忽略**
```

最恶劣的地方是**诊断全绿**：`khook=1 hth=1 hkl=0`、`kev` 还在涨，
只有 `dt` 冻住不再增长——所以之前几轮排查都被「钩子看起来正常」误导了。

**实测闭环**（`audit-2\hook\probe-poison-chain.out.txt`，合成真实鼠标注入）：

| 阶段 | 结果 |
|---|---|
| 基线干净双击 | `dt=1` ✔ 状态机可用 |
| 右键点一下（抬起被吞） | `IsAnyMouseButtonDown()=True`，`VK_RBUTTON=0x8000` |
| 中毒后再双击 | **`dt` 不涨 —— 完全被忽略** ★ 这就是用户看到的 |
| 在别处右键一次（抬起被放行） | `dt=2` 恢复（但用户不可能知道要这么做） |

修复的关键点有两个，缺一不可：

1. 判据不再读 `GetAsyncKeyState`，改用共享的**真实物理状态**；
2. 进程里有**两条**低级鼠标钩子，钩子链是**后装的先跑**——右键粘贴钩子先看到那条 up
   并吞掉它，守卫钩子**根本收不到**。所以必须由**吞掉抬起的那一方**
   （`BrowserHost.MouseProc`）主动调 `Native.NoteRmbUpSwallowed()` 更正共享状态。

### 根因二：`Hide()` 收尾里有一个**无超时的同步跨进程调用**

`BrowserHost.Hide()` 最后无条件调用 `EnsureNotTopmost()` → 同步
`SetWindowPos(hwnd, HWND_NOTOPMOST, …)`。这是跨进程调用，**目标线程不泵消息时它会一直等**。

`ToggleWindowCore`/`DoToggle` 永远跑在 **UI 线程**上（钩子线程只负责
`PostMessage(WM_APP_TOGGLE)`）。所以 UI 线程一旦卡在这个 `SetWindowPos` 里，
后面的 `WM_APP_TOGGLE` 永远排不到 → **双击 Ctrl 收不回去**。
（Chrome 的 UI 线程在弹原生菜单 / 模态期间确实会停止泵消息。）

**实测证据**（`audit-2\verify\ProbeNotTopmostFix.cs`，用反射调用**真实 exe 里**的
`BrowserHost.EnsureNotTopmost`，靶窗口线程先被 `SuspendThread` 冻结）：

| | 耗时 |
|---|---|
| 旧实现：同步 `SetWindowPos` | **4007ms 仍未返回**（探针等 4 秒放弃；`audit-2\host` 的 t1 实测 8000ms 都不返回） |
| 修复后：`BrowserHost.EnsureNotTopmost` | **2ms** |

### 修复内容

| 位置 | 改动 |
|---|---|
| `Native.cs` | 新增共享鼠标状态 + `NoteMouseButton` / `NoteRmbUpSwallowed` / `ResetMouseButtonState` / `IsAnyMouseButtonPhysicallyDown`；新增 `SWP_ASYNCWINDOWPOS`、`WS_EX_TOPMOST`、`WM_LBUTTONUP`、`WM_MBUTTONUP` |
| `HotkeyManager.cs` | 手势否决判据改用共享物理状态（不再读 `GetAsyncKeyState`）；`MouseProc` 记账按键状态；**`Release()` 补 `_active = null`**（见下） |
| `BrowserHost.MouseProc` | 吞掉右键抬起时调 `NoteRmbUpSwallowed()` 更正共享状态 |
| `BrowserHost.EnsureNotTopmost` | 先本地清 `WS_EX_TOPMOST` 样式位，再用**异步** `SetWindowPos` 兜底 → 永远立刻返回 |
| `BrowserHost` 的 `Show`/`SetVisibleCore`/`EnsureToolWindow`/置顶兜底 | 同步 `SetWindowPos` 全部补 `SWP_ASYNCWINDOWPOS` |
| `DeepSeekQuake.ToggleWindowCore` | 新增「重复请求合并」：请求投递时刻早于上次完成**且上次已生效** → 合并掉，不让窗口被自己按回来 |
| `DeepSeekQuake.UpdateTraceTitle` | 诊断串新增 `mg=`（合并次数）、`cap=0x…`（目标线程鼠标捕获）、`rmb=`（右键抬起被吞次数） |
| `verify\harness\Harness.cs` | `DEFER-01/02/05` 的 `Sleep(30)` → `Sleep(60)`，消除 flaky（见下方说明） |

**顺带修掉的第二个永久死状态**：`HotkeyManager.Release()` 原本只清 `_tapVk` 不清
`_active`，于是下一拍 `EnsureKeyboardHookAlive` 会把钩子**装回来**，而 `HandleKey`
开头 `if (_tapVk == 0) return;` 把所有按键丢掉 → 「钩子已装、诊断全绿、按键全无效」，
且唯一修复路径被「钩子已安装」挡住。触发条件：目标窗口句柄失效时保存一次设置。
已补 `_active = null`。

> 回归套件里原本有两条 **flaky 用例**（`DEFER-01` / `DEFER-05`）：harness 两次敲击之间只
> `Sleep(30)`，而产品的 `MIN_TAP_GAP_MS=40`，本机 Sleep 粒度约 15.5ms 使 30ms 实测取到
> 31ms 或 47ms → 取 31ms 时用例必然失败。实测 30 次：`DEFER-01` 过 18 次、`DEFER-05` 过 15 次。
> 这**不是**产品缺陷（`MIN_TAP_GAP_MS=40` 自 09-30 基线起就在），已把 harness 的
> `Sleep(30)` 改成 `Sleep(60)`（`DEFER-03` 那条刻意测「超时窗口」的用例保持原样），
> 改后 30 次全过（30/30、30/30）。

### 顺带修掉的靶场自身缺陷（**重要**）

`repro\FakeChrome.cs` 是按 `/target:winexe` 编译的，而它第 131 行直接调
`Console.OutputEncoding`——**没有控制台时这一行会抛异常**，且发生在第一次写日志之前。
结果：靶场自己崩掉、不产生任何日志，`run-repro.ps1` 只报「靶场没有产出日志」，
看起来像小工具的问题。**这个基准实验在修复前从来没真正跑起来过**
（`repro\mine.log`、`current.log`、`current2.log`、`current3.log` 全是这个状态）。
现已：`Console` 调用全部 try/catch、日志落盘失败不再静默（`_logWriteError`）、
`CreateWindowEx` 遇到窗口类残留（err=183/1407）时重试 30 次并如实记录。

### 目前掌握的事实（实测，不是推断）

- 用户的诊断报告里 **`hfail=0`**：`Hide()` **每一次都报告成功**，窗口也确实被置为不可见
  （`vis=0 style=0`）——**但用户看到的现象没消失**。这是最关键的一条矛盾。
- 同一报告里 `dt`（双击识别数）与 `tog`（切换执行数）完全相等，22/22、26/26，
  **说明按键识别和消息投递都没有丢**。
- `repro\probe-hide-real.exe`（反射驱动真实 exe）：连续 5 轮收起/呼出全部成功，
  `Hide()` 返回值与窗口真实可见性一致。
- 所有钩子常绿：`khook=1 hth=1 mhook=1 mgd=1`，`hkl=0`（钩子从未被摘掉）。

### 结论：还没找到根因

**证据链指向「工具的可见性判断与屏幕上的事实不一致」，但没能证实。** 可能性还剩：

1. **屏幕渲染残留**：`WS_VISIBLE` 已经清掉，但 Chromium 的合成器没重绘，
   用户看到的是一帧残影。这一条需要的检测手段是**抓屏对比**，我还没做。
2. **第二个窗口**：可能存在另一个属于同一 profile 的 Chrome 窗口，工具锁的是 A，
   用户看的是 B。用户的 `--status` 输出里只出现过一个 `Chrome_WidgetWin_1` 的 DeepSeek 窗口，
   但**没有做多窗口穷举**。
3. **「别的页面点不动」另有来源**：探针证实「隐藏的捕获持有者会抢点击」，
   但**没有**证实用户那台机器上真的发生了这件事（`capture=0x0` 出现过多次）。

### 下一步最该做的三件事（给接手的人）

1. **加抓屏验证**：`Hide()` 之后截取目标窗口矩形，与隐藏前的像素比对。
   这能一次性区分"真的还画着"和"只是状态位不对"。代码里已有 `BrowserHost.Hide()` 返回值
   和 `VisibleDiagnosis`，加一个 `Native.BitBlt` 抓屏即可。
2. **穷举同 profile 的所有顶层窗口**：`repro\` 里加个探针，枚举所有
   `Chrome_WidgetWin_1` + chrome.exe + 命令行含本项目 profile 的窗口，列出全部（不是只挑最大的）。
3. **让用户抓「卡住那一刻」的状态串**：现在状态串里有
   `hid=[vis= style= hung= pump= tries= pend=]` 和 `realhid=`，
   卡住时按 `Ctrl+Alt+D` 复制即可。重点看 `tries` 和 `realhid`——
   如果 `realhid=1` 但用户说还看得见，就锁定第 1 条（渲染残留）。

> 去掉会静默丢弃用户补救按键的切换去重守卫（改成「忙时合并 + 按结果决定补做」）；

> ——`ShowWindowAsync` 只是往目标线程的消息队列投一条请求，队列主人不处理时它
> 会**返回成功却什么都不做**，这就是「收不回去」的真正根因；
> 收起时清掉右键残留的鼠标捕获；键盘钩子被系统静默摘掉后能自愈；
> 置顶兜底加 `finally`；`Hide()` 改为返回 bool 并交叉核对真实可见性。
>
> ⚠️ 关于同步 `ShowWindow` 的一个更正：之前这里写着「绝不能用同步 ShowWindow」。
> 那是只看了它坏的一面——实测对**不泵消息**的窗口它确实会永久阻塞（`win32probe\out\p1_matrix.txt`
> CASE 5/6：45 秒不返回），但对**在泵消息**的窗口它是安全且唯一能保证生效的手段。
> 所以正确做法不是禁用，而是**先用 `SendMessageTimeout(WM_NULL, SMTO_ABORTIFHUNG)` 探测**，
> 确认安全再用。
