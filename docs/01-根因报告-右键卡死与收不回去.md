## ✅ 根因已找到并修复（2026-10-07 第二轮审计）

### 用户报告的现象

> 在窗口里**右键点击「非直接复制的区域」**（空白处、非输入框、非可选文本）之后，
> **双击 Ctrl 收不回去**，而且**除了这个窗口，别的页面也点不动**。
> 「一下就卡住」。

### 根因一（主因）：右键吞掉抬起 → 鼠标状态永久中毒 → 双击被无声否决

用户说的「一下就卡住」正是这个：**一次右键就够**，此后双击 Ctrl 完全无效，只能重启进程。

链路（每一环都有实测）：

```
用户在窗口里右键
  └─ 右键粘贴的钩子吞掉 WM_RBUTTONUP（return 1，为的是不让 Chrome 弹原生菜单）
       └─ 系统侧 GetAsyncKeyState(VK_RBUTTON) 的 0x8000 位**永远挂着**（没人清）
            └─ HotkeyManager 的旧判据 Native.IsAnyMouseButtonDown() 从此**恒为真**
                 └─ HandleKey 的 up 分支走「这一轮是鼠标手势」→ `_tapPending=false`
                      └─ 第一敲永不武装 → 此后**每一次双击都被静默忽略**
```

最恶劣的地方是**诊断全绿**：`khook=1 hth=1 hkl=0`、`kev` 还在涨，
只有 `dt` 冻住不再增长——所以之前几轮排查都被「钩子看起来正常」误导了。

**实测闭环**（`audit-2\hook\probe-poison-chain.out.txt`，合成真实鼠标注入）：

| 阶段 | 结果 |
|---|---|
| 基线干净双击 | `dt=1` ✔ 状态机可用 |
| 右键点一下（抬起被吞） | `IsAnyMouseButtonDown()=True`，`VK_RBUTTON=0x8000` |
| 中毒后再双击 | **`dt` 不涨 —— 完全被忽略** ★ 这就是用户看到的 |
| 在别处右键一次（抬起被放行） | `dt=2` 恢复（但用户不可能知道要这么做） |

修复的关键点有两个，缺一不可：

1. 判据不再读 `GetAsyncKeyState`，改用共享的**真实物理状态**；
2. 进程里有**两条**低级鼠标钩子，钩子链是**后装的先跑**——右键粘贴钩子先看到那条 up
   并吞掉它，守卫钩子**根本收不到**。所以必须由**吞掉抬起的那一方**
   （`BrowserHost.MouseProc`）主动调 `Native.NoteRmbUpSwallowed()` 更正共享状态。

### 根因二：`Hide()` 收尾里有一个**无超时的同步跨进程调用**

`BrowserHost.Hide()` 最后无条件调用 `EnsureNotTopmost()` → 同步
`SetWindowPos(hwnd, HWND_NOTOPMOST, …)`。这是跨进程调用，**目标线程不泵消息时它会一直等**。

`ToggleWindowCore`/`DoToggle` 永远跑在 **UI 线程**上（钩子线程只负责
`PostMessage(WM_APP_TOGGLE)`）。所以 UI 线程一旦卡在这个 `SetWindowPos` 里，
后面的 `WM_APP_TOGGLE` 永远排不到 → **双击 Ctrl 收不回去**。
（Chrome 的 UI 线程在弹原生菜单 / 模态期间确实会停止泵消息。）

**实测证据**（`audit-2\verify\ProbeNotTopmostFix.cs`，用反射调用**真实 exe 里**的
`BrowserHost.EnsureNotTopmost`，靶窗口线程先被 `SuspendThread` 冻结）：

| | 耗时 |
|---|---|
| 旧实现：同步 `SetWindowPos` | **4007ms 仍未返回**（探针等 4 秒放弃；`audit-2\host` 的 t1 实测 8000ms 都不返回） |
| 修复后：`BrowserHost.EnsureNotTopmost` | **2ms** |

### 修复内容

| 位置 | 改动 |
|---|---|
| `Native.cs` | 新增共享鼠标状态 + `NoteMouseButton` / `NoteRmbUpSwallowed` / `ResetMouseButtonState` / `IsAnyMouseButtonPhysicallyDown`；新增 `SWP_ASYNCWINDOWPOS`、`WS_EX_TOPMOST`、`WM_LBUTTONUP`、`WM_MBUTTONUP` |

已补 `_active = null`。

## 第三轮：2026-10-08 —— 「收起后别的窗口左键点不动，非得再右键一下才恢复」

### 用户报告

> 如果在 deepseek 里面点击了右键，收回后，左键无法直接与其他界面交互，像被锁住一样，
> 要先点一下右键，才能解除锁住。（追问确认：**每次必现**；解锁用的右键**点在哪里都行**）

### 判断：就是上面风险表里那一条，但当时只做了一半

症状完全落在**症状二（别的页面点不动）**上：右键粘贴吞掉 `WM_RBUTTONUP` → 浏览器把鼠标
捕获攥住 → 窗口被收起，而**捕获不随隐藏消失**（本文早前已实测）→ 隐藏的持有者继续抢走
全桌面点击 → 用户「点哪都不动」；再点一下右键，那条迟到的抬起才让浏览器松手，
所以表现为「右键一下就解锁」。

v2.1 的收尾只做了**一件事**：补发一条 `WM_CANCELMODE` 并校验，**清不掉时仅记日志**。
问题在于 `WM_CANCELMODE` 是「请求对方自己放手」——`DefWindowProc` 收到才会
`ReleaseCapture`，而 Chrome 是**另一个进程**，可以不处理这条消息。

### 修法：三道防线 + 心跳兜底，全都不依赖对方配合

| 顺序 | 手段 | 为什么 |
|---|---|---|
| 1 | 补发 `WM_CANCELMODE` | 最干净、代价最小；对方愿意处理就结束 |
| 2 | **强制夺回**：`SetCapture(本线程的隐藏窗口)` → `ReleaseCapture()` | 系统同一时刻只允许一个窗口持有捕获，原持有者立即收到 `WM_CAPTURECHANGED` 而放手。**不需要对方配合**；也不会像补发 `WM_RBUTTONUP` 那样把 Chrome 原生菜单弹出来 |
| 3 | 再补发一次 `WM_CANCELMODE` | 第一道有时正撞上目标线程忙，重发往往就过了 |

再加 `BrowserHost.CaptureWatchdog`（心跳每拍，仅在**窗口确实已收起**且仍有捕获时动手，
节流 1 秒）：漏网也会在 ≤1 秒内自愈，而不是要用户手动右键。
可见时不清理——那时的捕获可能是用户在正常拖拽/选词。

### 顺带修掉：`Hide()` 只覆盖了一半的「前台悬空」

原来只在 `wasOurs`（收起前它是前台）时才交还前台。还有一种更隐蔽的情况：**收起之后前台
仍然指着那个已经藏起来的窗口**（浏览器/自定义外壳下 `SetForegroundWindow` 会被前台锁拒绝，
本文档上一轮已记录过 `set=True` 却提不到前台的实测）。这时桌面上等于没有前台，

### 判断：检测盲区把整条防线静默跳过了

`CaptureWindowOf` 靠 `GetGUIThreadInfo` 读目标线程的 `hwndCapture`，而它
**查询失败时同样返回 `IntPtr.Zero`**。「没有捕获」与「查不到」在返回值上无法区分，于是：

```
GetGUIThreadInfo 查失败
  └─ CaptureWindowOf 返回 0
       └─ ForceDropCapture 见 0 就 return true 早退
            └─ TryReleaseCapture 查不到也返回「已清空」
                 └─ 整条防线被跳过，包括唯一能跨进程强夺、
                    且完全不依赖对方配合的 StealCapture
```

结论：**v2.2 的三道防线没错，错在「只有检测到才动手」。** 检测一旦失灵，
防线就整体失效——日志干净、诊断全绿、问题依旧，恰好与用户「每次必现」的体感吻合。

### 修法

1. **收起路径不再信检测**：`ForceDropCapture("收起", forceSteal: true)`。
   每次收起都强制夺回一次；夺回不需要知道对方是谁（系统同一时刻只允许一个窗口持有捕获），
   成本约 0ms，也不弹 Chrome 原生菜单。
2. **把盲区做成可见的数字**：`TryReleaseCapture` 查询失败不再算「已清空」，改为返回 false
   并累加 `_gtiFailures`（诊断串 `gterr=`）。**`gterr>0` 就证明 `cap=0x0` 不可信**。
3. **心跳两档节流**：收起后 3 秒内每拍都扫（用户就是在这几秒里去点别的窗口的），
   之后退到 1 秒一次；敏感期内同样走 forceSteal，不信检测。
4. **堵上第二条「锁住鼠标」的路**：菜单/移动缩放**模态循环会自己吃掉点击**，
   症状与捕获残留一模一样但机制不同。除 `hwndFocus` 外，再向 `hwndMenuOwner` /
   `hwndMoveSize` 补发 `WM_CANCELMODE`。

### 新增诊断：把四种「点不动」彻底分开

v2.2 只能分辨「捕获残留」与「前台悬空」。v2.3 补齐另外两种机制：

| 字段 | 机制 | 正常值 |
|---|---|---|
| `cap=` | 捕获残留在别人手里 | `0x0`（但**要先看 `gterr`**） |
| `gterr=` | 检测失败次数 | `0`；**>0 说明 `cap=0x0` 不可信** |
| `fsteal=` | 强制夺回次数 | 随每次收起增长属正常 |
| `owncap=` | 我们自己攥着捕获 | `0x0` |
| `clip=` | 光标被 `ClipCursor` 困住 | `0` |
| `gtiflg=` / `gtimen=` | 菜单模态循环在吃点击 | `0` / `0x0` |
| `fgw=` | 前台悬空 / 悬在已收起的窗口上 | `v1` 且 `m0` |

## 第五轮：2026-10-08（v2.4 → v2.5）——**定案：鼠标按键「假按下」**，并修复

### 现场证据（v2.4 报告，决定性）

报告者原话：「还是一样，我不小心多点了两下」。报告里的关键一行：

```
btn=L-/R!/M-/sh L-/R-/M-
```

- `btn=R!` —— `GetAsyncKeyState(VK_RBUTTON)` 的 `0x8000` 位是 1：**系统认为右键按着**；
- `sh` 的 `R-` —— 低级钩子记账里右键**已经松开**（真实物理状态）；
- 两者不一致 = **「假按下」**，不是误读、不是采样时机问题。

同一份报告里其余全部阴性，把前几轮的假设逐一钉死：

```
stealfrom=0x0     夺回时「上一个捕获窗口」为 0 → 根本没人攥着捕获
stealn=7/7        7 次强制夺回，7 次都「夺到」又立刻放手（夺到的是空气）
cap=0x0           没有捕获残留
gterr=0           捕获检测从未失败（「检测盲区」假设不成立）
clip=0            光标没被裁剪
gtiflg=0x0 / gtimen=0x0    没有菜单模态
fgw=0x0/v0/m0     前台是 NULL
```

左键探针（v2.4 新加的观测）记到：

```
左键探针: 第 1 下点(x,y) 眼睛看到=0x… 点击前前台=0x60106 → 点击后前台=0x0
```

**点击之后前台变成了 NULL** —— 这一下不但没切前台，还把前台搞没了。
这正是「系统认为有鼠标键按着」时的典型行为：点击被当成**一次尚未结束的拖拽**，
不参与窗口激活。

### 因果链（定案）

```
右键粘贴：为了不让 Chrome 弹原生右键菜单，钩子吞掉 WM_RBUTTONUP（return 1）
      │
      ├─► 那次抬起**从未进入系统输入流**
      │        └─► GetAsyncKeyState(VK_RBUTTON) 的 0x8000 位**一直挂着**
      │              （本仓库早就注释记录过这个性质，见 Native.IsAnyMouseButtonDown）
      │
      └─► 于是系统层面：**用户早就松手，系统却认为右键按着**
               │
               ├─► 后续鼠标点击被当作「拖拽还没结束」
               │        └─► **点击不再激活窗口**（前台不切换，甚至变成 NULL）
               │
               └─► 用户看到：收起之后左键像被锁住，点别的窗口毫无反应
                        └─► 而「随便点一下右键就恢复」
                             = 补上一次抬起，把那个假状态清掉
```

**为什么前两轮都修错了方向**：这条路径**不产生任何显式捕获**。
`cap=0x0`、`owncap=0x0`、`stealfrom=0x0`、`gterr=0` —— 四项常规诊断**全部阴性**，
而问题依旧。v2.2（三道防线清捕获）、v2.3（强制夺回 + 检测盲区）都在查捕获，
所以报告者说「改了跟没改一样」。

**这也是「查不到 ≠ 没有」那条教训的第二次应验**：v2.3 修的是「检测有盲区时别跳过」，
方法对，但查的对象本身就不是元凶。

### 修法

**`BrowserHost.PumpStuckMouseButtons(why)`** —— 往输入流里补一条**合成抬起**
（`SendInput` + `MOUSEEVENTF_*UP`），把假按下状态抹掉。它不是「缓解症状」，
而是**直接消掉造成症状的那个状态**：做完之后点击会重新激活窗口。

关键设计与理由：

1. **只注入「抬起」，绝不注入「按下」。** 凭空替用户按一下鼠标是绝对不行的。
2. **只修「系统说按着 + 钩子记账说已松开」的键。** 物理上真按着的键一律不碰，
   否则会把用户正在按的键强行抬起来（拖拽会被打断）。
   `Native.SharedButtonDown(vk)` 提供这份真实状态。
3. **用户手上正拿着鼠标时一概不动手**（有键物理按着就返回，等下次）。
   下面第 4 点要抢一次捕获，而抢走捕获会直接打断他的拖拽。
4. ★ **注入前先把自己（UI 线程那个不可见消息窗口）设成捕获窗口。**
   合成抬起是**系统级**输入：它会投递给「当前持有捕获的窗口」，没有捕获时才给
   光标下的窗口。直接注入的话，这条 up 会落到
   - 光标下的任意程序 → 在那边弹出一个右键菜单，或
   - 正在显示的目标窗口 → Chrome 收到 `RBUTTONUP` 就弹它自己的原生菜单，

   恰恰是「吞掉抬起」要避免的东西。系统同一时刻只允许一个窗口持有捕获，
   所以先抢过来，这条 up 就只会投给我们自己那个**没有菜单的窗口**
   （`DefWindowProc` 对它什么都不做）。
5. **注入后 `Thread.Sleep(25)` 再 `ReleaseCapture`。** `SendInput` 只负责把事件
   塞进输入流，真正的投递发生在那之后；立刻放手会留一个竞态，让这条 up 又跑到
   光标下的窗口去。25ms 远小于低级钩子的 300ms 超时。
6. **带节流（200ms）并回读真实状态**，把「注入前 → 注入后」记进日志（诊断串 `plum=[…]`）。
   修复**必须可自证**：`R!→R-` 才算修好，`R!→R!` 就说明这条抬起没进输入流。

**两个触发点**：

| 触发点 | 为什么 |
|---|---|
| `Hide()` 收起收尾（同步执行） | 用户症状就发生在这一刻；此时窗口已经藏起来，即便捕获重定向失败也不会弹出可见菜单（双保险） |
| 右键粘贴后 ~300ms（心跳执行） | 让工具在**没有收起**时也能自愈；延迟是为了等浏览器把这次右键处理完（菜单判定、选区、光标位置） |

### 先验证假设，再让用户去试

v2.2 / v2.3 的教训是「按假设改完 → 用户回『没啥区别』」。所以这一版新增
`--mousetest`：**先把机制和真实函数都单独跑通**，不依赖真实右键操作。它分两个阶段，
第二阶段是最有价值的一步——**把状态重新弄脏、并放开捕获**（前置条件与用户现场
完全一致：`btn=R!`、没有人持有捕获＝`cap=0x0`），再调产品里那个真实的
`PumpStuckMouseButtons`：

```
========== DeepSeek Quake 鼠标状态探针 v2.5 ==========
目的: 验证「注入合成抬起能清掉系统层面的假按下状态」，并跑一遍真实修复函数

起始状态: L-/R-/M-   钩子记账: L-/R-/M-
把自己设为捕获窗口: 成功（成功 = 下面的 down/up 只会投给我们自己，桌面收不到）
① 注入右键按下 → L-/R!/M-   [OK] 系统进入「按着」状态（= 抬起被吞掉后的等价状态）
② 注入右键抬起 → L-/R-/M-   [OK] 假按下状态被清掉 —— v2.5 的修法成立

---- 第二阶段：调用产品里真实的 BrowserHost.PumpStuckMouseButtons ----
重新弄脏后放开捕获: L-/R!/M-（钩子记账 L-/R-/M-  我们持有捕获=False）
函数返回=True  修完状态=L-/R-/M-   [OK] 真实修复函数自己抢捕获、注入、回读确认，全部走通
它自己记录的结论: 已注入合成抬起(R) L-/R!/M-→L-/R-/M- 因:自检

最终状态: L-/R-/M-   （必须是 R- 才算干净）

```

- ① 复现了「抬起消失 → 系统保持在按着」这一步（等价于「被吞掉的抬起」的后果）；
- ② 证明注入抬起能把它清掉；
- 第二阶段证明：**在没有人持有捕获的条件下**，产品代码自己能抢到捕获、把这条 up
  重定向给自己、注入、并回读确认清干净，还留下了与文档一致的那行日志；
- **安全性**：全程由本进程的隐藏窗口持有捕获，桌面收不到任何点击、光标不动；
  **取不到捕获就直接放弃、绝不注入**（否则那一下会落到光标下的任意程序上）；
  收尾再补三次抬起并回读确认，绝不把「按着」留在系统里。全程约 300ms。

### 验证状态（如实记录）
