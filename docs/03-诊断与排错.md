# 诊断与排错

> 从原 README 拆分而来：自检与诊断窗口、诊断串字段速查表，
> 以及「收不回去」这类深层故障的对照表。

## 自检与诊断

托盘右键 →「**自检与诊断…**」，一眼看到卡在哪一环：

```
──── 1. 浏览器外壳 ────     找到哪些浏览器、当前用哪个、上次启动失败的原因
──── 2. 目标窗口 ────       有没有锁定窗口、可见性、是否已排除任务栏
──── 3. 热键 ────           配置值 / 实际生效值 / 组合键注册成功没 / 键盘钩子装上没
──── 4. 右键粘贴 ────       钩子装没装、右键按了几次、真正注入 Ctrl+V 几次
──── 5. 内部状态 ────       实时状态串
──── 6. 事件日志 ────       最近 60 条内部事件
```

- **「测试启动浏览器」**：手动跑一遍启动流程，直接告诉你成功还是失败、失败在哪一步；
- **「复制全部」**：整份报告复制到剪贴板，贴给谁都行；
- 命令行一键验证（小工具运行时）：`pwsh -File tests\verify-quake.ps1`。

小工具**不写日志文件**（原因见 [开发与编译](02-开发与编译.md)），所以诊断信息都在这个窗口里。

**双击 Ctrl 收不回去 / 别的页面也点不动？（2026-10-07 二次修复）**

**真正的根因**：收起和呼出原先都只用 `ShowWindowAsync`。它只是往目标窗口的消息队列
**投一条请求**就立刻返回——队列主人不处理时，它会**返回成功却什么都不做**。
于是「收起」报成功、窗口却还在屏幕上，你再按一次热键，工具看到"窗口已经不可见"
就执行"呼出"，结果什么也没变——这就是「怎么按都收不回去」。

实测证据：`win32probe\out\p1_matrix.txt` CASE 4 —— 对不泵消息的窗口调
`ShowWindowAsync(SW_HIDE)`，0~2ms 返回 `True`，而 `IsWindowVisible` 始终是 `True`。

**修法**：两个方向都改成两阶段——先异步短重试（便宜、绝不阻塞），确认目标线程
在泵消息之后再用同步 `ShowWindow` 兜底（一定生效）。同步调用会先探测
`SendMessageTimeout(WM_NULL, SMTO_ABORTIFHUNG)`，只有确认安全才用，避免在
不泵消息的窗口上永久阻塞。

验证：`repro\probe-hide-real.exe` 用反射驱动真实 exe 的 `Hide()`/`Show()`，
连续 5 轮收起/呼出全部成功（`PASS=8 FAIL=0`）。

另外两处相关问题：
- 右键抬起被吞掉会留下鼠标捕获，而**持有捕获的窗口即使被隐藏，仍会把点击抢走**
  （实测 `win32probe\out\p5_rbutton.txt`）——所以收起时会顺手清掉，日志写
  「已清掉残留的鼠标捕获」；
- 键盘钩子被系统静默摘掉后能自愈（见下面表格的 `hkl=`）。

| 看哪里 | 含义 | 怎么办 |
|---|---|---|
| 第 3 节「因『键按了但钩子没报』重装次数」> 0 | 键盘钩子被 Windows 静默摘掉过，工具已自动装回来 | 不用管，说明自愈生效了；次数一直在涨才需要反馈 |
| 第 5 节 `hkl=` | 同上（自愈次数） | 同上 |
| 第 5 节 `hfail=` | 累计「收起没能确认生效」次数 | 少数几次正常（浏览器忙）；一直在涨说明浏览器本身卡住了 |
| 第 5 节 `hid=[...]` | **收起时的现场快照**：`vis=`可见性 / `style=`WS_VISIBLE样式位 / `hung=`浏览器无响应 / `pump=`浏览器在不在处理消息 / `tries=`这次试了几次才成功 / `pend=`有没有待复核 | `pump=0` 说明浏览器自己卡住了（不是本工具的错）；`tries` 明显大于 1 说明异步指令不够用、已经靠同步兜底救回来了 |
| 第 5 节 `realhid=` | 交叉核对后的「真的隐藏了没有」 | 应该是 1（收起后）/ 0（呼出后） |
| 第 5 节 `showfail=` | 累计「呼出没能确认生效」次数 | 同上，一直涨要反馈 |
| 第 5 节 `slow=` | UI 消息循环卡顿（>1.5 秒）次数 | 应该是 0；不是 0 请反馈，说明还有地方在阻塞 |

| 第 5 节 `capfix=` | 累计**清掉的残留捕获次数**。>0 说明「隐藏窗口攥着捕获」确实发生过，而且工具已经自己收拾干净了 | 不用处理；它证明 v2.2 的修复在起作用。数值一直在涨也可以反馈 |
| 第 5 节 `fgw=0xXXXX/v?/m?` | 此刻**前台窗口的指纹**：句柄 / 是否可见（v）/ 是不是我们的目标窗口（m） | 收起后出现「点一下才恢复」时看它：`v0` = 前台悬在一个已经藏起来的窗口上；`m1` = 前台还指着我们收起的窗口 |

| 第 5 节 `gterr=` | **捕获检测失败的累计次数**（v2.3）。`CaptureWindowOf` 靠 `GetGUIThreadInfo`，而它在查询失败时同样返回 `0` —— 与「真的没有捕获」在返回值上无法区分 | **应该是 0**；`>0` 就说明 `cap=0x0` 不可信、只是查不到。请连同 `cap=` 一起反馈 |
| 第 5 节 `fsteal=` | 累计**强制夺回**次数（v2.3）。收起路径不再只信检测，每次收起都夺一次 | 随每次收起增长属正常 |
| 第 5 节 `owncap=0x…` | **我们自己**的 UI 线程持有的鼠标捕获（v2.3） | 正常恒为 `0x0`；非 0 说明是我们自己变成了那个「隐藏的捕获持有者」，请反馈 |
| 第 5 节 `clip=0/1` | 光标有没有被 `ClipCursor` 困在一个比虚拟屏幕更小的矩形里（v2.3）。它与鼠标捕获并列，是第二种能造成「全桌面点不动」的机制 | 应该是 `0`；为 `1` 时鼠标会被困在小矩形里，请反馈 |
| 第 5 节 `gtiflg=0x…` / `gtimen=0x…` | 目标线程的**模态位**与菜单宿主窗口（v2.3）。菜单模态循环会**自己**吃掉点击，症状与捕获残留一模一样但机制不同 | `gtiflg` 含 `0x4/0x8/0x10`，或 `gtimen` 非 0，就说明是菜单在吃点击，而不是捕获 |
| 第 5 节 `btn=L?/R?/M? /sh L?/R?/M?` | **系统层面的鼠标按键状态**（`GetAsyncKeyState` 的 0x8000 位）与**钩子看到的真实物理状态**（v2.4）。`!` = 按着 | **最关键的一对**：`btn` 里有 `!` 而 `/sh` 同一位是 `-`，就是「假按下」的指纹（右键抬起被吞掉的后遗症），请反馈 |
| 第 5 节 `stealfrom=0x…` / `stealn=a/b` | 强制夺回时 `SetCapture` 的返回值——**全系统唯一能问到「谁攥着捕获」**（v2.3）。`a`=调用次数，`b`=真的夺到次数 | `stealfrom` 正常为 `0x0`；**非 0 就是攥着捕获的那个窗口的句柄**（真凶指纹）。`stealn` 长期 `a/b` 相等且 `b>0` 说明总有人攥着 |
| 第 5 节 `probe=` + 事件日志「左键探针」 | 收起后**那第一下左键到底发生了什么**（v2.4）：点在哪、眼睛看到的是哪个窗口、点击前后前台有没有变。只观测、绝不吞消息 | 「点击后前台」没变 = 这一下被吃掉了；变了但用户仍觉得没反应 = 问题不在输入路由 |
| 第 5 节 `pumps=` / `plum=[…]` | 注入**合成抬起**（修假按下状态）的次数与最近一次的「注入前→注入后」（v2.5） | `pumps>0` 说明发生过「假按下」且已修；`plum` 期望 `…R!→R-…`，若是 `R!→R!` 请反馈 |
| 事件日志里「收起未确认：浏览器没有响应窗口命令」 | **不是本工具的错**：浏览器 UI 线程此时不在处理窗口消息（卡住/模态），异步隐藏指令投不进去 | 再按一次热键；或等浏览器缓过来 |
| 事件日志里「显示后窗口仍不可见」 | 呼出这一步也没能确认生效 | 把 `hid=[...]` 一起贴给我 |

一个反直觉但很重要的细节：**隐藏一个已经持有鼠标捕获的窗口，并不会释放它的捕获**。
它照样会把之后所有点击抢走，你会觉得「整个桌面点不动」。这就是为什么「收起」里必须
显式清捕获，而不是指望窗口一藏就没事了。

**「收起后别的窗口左键点不动，像被锁住，得先点一下右键才恢复」？（2026-10-08 第三次修复，v2.2）**

链路（每一环都有实测）：

```
右键粘贴为了不弹 Chrome 原生菜单 → 钩子吞掉 WM_RBUTTONUP
  └─ 浏览器认为「右键还按着」→ 把鼠标捕获攥在手里
       └─ 窗口被收起、隐藏 —— 但**捕获不会随隐藏一起消失**
            └─ 隐藏的捕获持有者把之后所有点击都抢走 → 「点哪都不动」
                 └─ 用户再点一下右键 → 那条迟到的 WM_RBUTTONUP 让浏览器松手
                      └─ 于是表现为「右键一下才解锁」
```

v2.1 只做了「补发一条 `WM_CANCELMODE` 并校验」，**清不掉时仅记日志**（根因报告的风险表里
把这条列为「中」风险，并注明「若再遇到『别的页面点不动』，先看 `cap=` 是否非 0」）。
而 `WM_CANCELMODE` 要靠对方配合：`DefWindowProc` 收到才会 `ReleaseCapture`，
但 Chrome 是别的进程，完全可以不处理。

v2.2 改成三道防线，且都不依赖对方配合：

1. 补发 `WM_CANCELMODE`（最干净）；
2. **强制夺回**：把自己 UI 线程里的隐藏消息窗口 `SetCapture`，系统只允许一个窗口持有捕获，
   原持有者立刻收到 `WM_CAPTURECHANGED` 而放手，随后马上 `ReleaseCapture`——
   既不靠对方配合，也不会弹出 Chrome 原生菜单（对比：补发 `WM_RBUTTONUP` 会弹菜单）；
3. 再补发一次 `WM_CANCELMODE`。

外加**心跳兜底** `CaptureWatchdog`：窗口确实收起、而目标线程仍握着捕获时，每拍清一次
（`capfix=` 计数），所以漏网也会在 ≤1 秒内自愈。**窗口可见时不清理**，因为那时捕获可能
是用户在正常拖拽/选词。

同时把 `Hide()` 交还前台的判据从「收起前它才是前台」放宽为「收起前它是前台 **或** 收起后
前台仍悬在它身上」——后者会让之后的第一下点击只被拿去「指定前台」，现象极像同一件事。
诊断串新增 `capfix=` 与 `fgw=0xXXXX/v?/m?` 用来区分这两种情况。

**「v2.2 之后还是一样」——第四次修复（2026-10-08，v2.3）**

报告者实测反馈（附完整自检报告）：「还是一样啊」。而报告里 `capfix=2`、`cap=0x0` ——
**清捕获的代码确实跑过两次、此刻也确实没有捕获**，问题却照旧。这说明 v2.2 的三道防线
本身没错，**是判据有洞**：

```
CaptureWindowOf 靠 GetGUIThreadInfo 读对方线程的 hwndCapture
  └─ 但查询失败时它同样返回 IntPtr.Zero
       └─ 「没有捕获」和「查不到」在返回值上无法区分
            └─ ForceDropCapture 见 0 就 return true 早退
                 └─ TryReleaseCapture 查不到也返回「已清空」
                      └─ 整条防线被静默跳过 —— 包括唯一能跨进程强夺、
                         且完全不依赖对方配合的 StealCapture
```

于是「日志干净、诊断全绿、问题依旧」。

v2.3 的改法：

1. **收起路径不再信检测**：`ForceDropCapture("收起", forceSteal: true)` ——
   每次都强制夺回一次。夺回不需要知道对方是谁（系统同一时刻只允许一个窗口持有捕获），
   成本约 0ms，也不弹原生菜单；
2. **让盲区变成可见的数字**：`TryReleaseCapture` 查询失败不再算「已清空」，
   改为返回 false 并累加 `_gtiFailures`（诊断串的 `gterr=`）。**`gterr>0` 就说明
   `cap=0x0` 不可信**；
3. **心跳两档节流**：收起后 3 秒内每拍都扫（用户就是在这几秒里去点别的窗口的），
   之后退到 1 秒一次；敏感期内同样走 forceSteal；
4. **把「另一条能锁住鼠标的路」也堵上**：菜单/移动缩放模态循环会**自己**吃掉点击，
   所以除 `hwndFocus` 之外，再向 `hwndMenuOwner` / `hwndMoveSize` 补发 `WM_CANCELMODE`。

诊断串同时新增 `fsteal=`、`owncap=`、`clip=`、`gtiflg=`、`gtimen=`（含义见上表），
用来把四种会造成「点不动」的机制彻底分开：捕获残留 / 前台悬空 / 菜单模态 / 光标裁剪。

**四种机制全被排除之后：第五次，改为「取证」（2026-10-08，v2.4）**

v2.3 交付后的自检报告里，上面那批字段**全是阴性**：`gterr=0`、`cap=0x0`、
`owncap=0x0`、`clip=0`、`gtiflg=0x0`、`gtimen=0x0`，而 `fsteal=26`（强制夺回跑了 26 次
却什么也没夺到）。**结论是硬的：这四种机制都不是元凶。**

于是 v2.4 不再猜，改为直接取证，新增三样：

| 观测 | 回答什么问题 |
|---|---|
| `btn=`（+ `/sh` 真实物理状态） | **系统是不是认为某个鼠标键一直按着。** 右键粘贴吞掉 `WM_RBUTTONUP` 后 `VK_RBUTTON` 的 0x8000 位会一直挂着（见 `Native.IsAnyMouseButtonDown` 的警告）——用户早松手了，系统却认为还按着。**这条路径不产生任何显式捕获**，所以 `cap` 照样是 `0x0` |
| `stealfrom=` / `stealn=` | **到底有没有人攥着捕获。** `SetCapture` 的返回值就是上一个捕获窗口，这是全系统唯一能问到「谁攥着捕获」的办法（`GetCapture` 只答本线程，`GetGUIThreadInfo` 只答指定线程）。**非 0 就说明有人攥着，哪怕 `cap=0x0`** |
| 事件日志「左键探针」 | **收起后那第一下左键到底发生了什么**：点在哪、眼睛看到的是哪个窗口、点击前后前台有没有变。只观测、绝不吞消息 |

探针输出形如：

```
左键探针: 第 1 下点(812,455) 眼睛看到=0x1A0B2C[Chrome_WidgetWin_1/pid=12345] 点击前前台=0x5A1586 → 点击后前台=0x1A0B2C → 已切换，这一下生效了
```

- 若「点击后前台」**没变** → 这一下点击被吃掉了（真·输入锁）；
- 若**变了**但用户仍觉得没反应 → 问题不在输入路由，而在别处（页面状态 / 目标程序自己）。

读报告时的顺序建议：先看 `btn=` 有没有 `!`，再看 `stealfrom=` 是否非 0，
最后看事件日志里的「左键探针」。

**取证定案 + 修复（2026-10-08，v2.5）**

v2.4 的报告给出决定性证据——`btn=` 那一行：

```
btn=L-/R!/M-/sh L-/R-/M-
```

**`R!` = 系统认为右键还按着；`sh` 的 `R-` = 钩子看到的真实物理状态是已松开。**
两者不一致，就是「**假按下**」的指纹。同一份报告里 `stealfrom=0x0`、`stealn=7/7`（七次
强制夺回全部扑空）、`gterr=0`、`cap=0x0`、`clip=0`、`gtiflg=0x0`、`gtimen=0x0`
继续全阴性；左键探针记到「点击前前台=0x60106 → 点击后前台=0x0」，即**点击不再激活窗口**。

因果链与修法见 [根因报告 第五轮](01-根因报告-右键卡死与收不回去.md)。
一句话：**右键粘贴吞掉 `WM_RBUTTONUP` → 系统层面的 `VK_RBUTTON` 一直是「按下」
→ 点击被当成「拖拽未结束」、不再激活窗口 → 收起后点别的窗口没反应；
而「再点一下右键」正好等于补上那次被吞掉的抬起。**

**上线确认**：v2.5 交付后，报告者重启并按原步骤使用（呼出 → 页面右键粘贴 → 收起 →
直接点别的窗口），回复「**可以了**」——症状消失（2026-10-08 21:20）。这是该问题四轮
排查以来第一次由现场确认闭环；本文件下面的字段仍保留，作用是**万一复发时一眼定位**。

### 新增字段

| 字段 | 含义 | 正常值 / 怎么办 |
|---|---|---|
| 第 5 节 `pumps=` | 累计**注入合成抬起**的次数（v2.5）。用来把「被吞掉抬起留下的假按下状态」抹掉 | `>0` 说明确实发生过「假按下」，而且已经修过；`0` 说明没发生过 |
| 第 5 节 `plum=[…]` | 最近一次注入的「**注入前 → 注入后**」与原因（v2.5） | 期望 `…R!→R-…`（修好了）；若一直是 `R!→R!`，说明这条抬起没进输入流，**请反馈这一行** |

事件日志里对应的两条：

```
已注入合成抬起(R) L-/R!/M-→L-/R-/M- 因:收起
被卡住的鼠标状态已清干净（R）——收起后左键应该能直接点别的窗口了
```

### `--mousetest`：先验证假设，再交付
